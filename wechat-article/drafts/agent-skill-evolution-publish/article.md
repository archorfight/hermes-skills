# Anthropic 内部已经在让 AI 自己写 AI 了，我拆出了 3 招

Anthropic 的 Claude Code 负责人 Boris 最近在一个播客里说了一句话：

> 「Claude Code 本身，现在已经是 100% 使用 Claude Code 开发的。」

**写 AI 的 AI，是用 AI 自己写的。** 从去年 Opus 4.5 时期就开始了。

我用 Agent 跑了大半年，写了 **15 个 Skill**，累计调用超过 **2000 次**。公众号 36 篇文章，大部分是 Agent 产初稿我再微调。选题、大纲、审计、排版，全自动化。

**我不小心抄了 Anthropic 的作业。** 他们的方法论，我拆出了三招。

---

## 第一招：别当码农了，当项目经理

Boris 描述的 Anthropic 内部工作状态是这样的：

白天，工程师像项目经理一样给 AI 分配任务。晚上，他们像云计算调度员一样，同时运行数百个 Agent。

> **不是一个人写代码，是一个人管几百个写代码的 AI。**

这跟大多数人的用法完全不同。大部分人用 AI 编程，还是一个对话窗口，一段一段地生成。效率比手写快，但没有本质区别。

Anthropic 的做法本质上是：**你不是在写代码，你是在设计一个「代码生产系统」。**

你写清楚要什么。Agent 负责怎么做。写完自动跑测试，不通过就自己改，改到通过为止。

> 你只看结果和架构设计，代码是 Agent 的事。

这招我直接抄了。我的公众号从选题到大纲到初稿到审计到发布，整个流程都是 Agent 在跑。我只负责选题确认和最终微调。

**一个人干五个人的活，不是因为写得多快，是因为你不再自己写了。**

## 第二招：别装别人的 Skill，自己写

一个叫阿真的博主说了句大实话：她装了百八十个 Skill，大部分从来没调用过。

别人的 Skill 你看不懂它到底干了什么。那些带脚本、能操作文件、能执行命令的，装进来等于给了它更多权限。**用了不放心，不用又白装。**

我自己的数据更扎心：装了别人推荐的 20 多个 Skill，**实际调用的不到 5%**。但我自己写的 15 个，每一个都反复用了上百次。

原因就一个：**自己写的 Skill，你知道它的边界在哪。别人的，你不知道。**

后来我想明白了一件事：好 Skill 和烂 Skill 的区别，不在提示词写得好不好，在于**它的结构能不能持续迭代**。

有个方法论提了一个黄金比例：**规划 2 小时，执行 10 分钟，审查 1 小时。**

大部分人用 AI，是反过来——花 2 分钟想想需求，让 AI 跑 10 小时，最后审查 0 分钟。产出自然不行。

> 你的 Skill 不是一次性脚本。它应该是越用越好用的工具。

## 第三招：让 Agent 自己变强

Boris 还透露了一点：Anthropic 内部已经出现了「AI 写 AI」的闭环。虽然还不是完全自动递归，但方向很明确——**Agent 不只是工具，它应该能自己进化。**

这一点最让我兴奋。

我在自己的系统里跑了一个简化版。

每天，我的 Agent 做三件事：复盘当天的工作效果，把踩过的坑写入记忆文件，根据复盘结果更新 Skill 的指令。

听起来很复杂？核心就是一个框架：**进化 GPS + 安全带。**

进化 GPS 决定往哪进化：稳定性第一，可解释性第二，可复用性第三。复用频率高的能力优先进化。

> 安全带防止乱进化：不引入无法验证的机制，不把「感觉正确」当决策依据，每次进化必须能回滚。

简单说：**可以变强，但不能变疯。**

<!-- IMAGE:chart3 -->

我跑了大半年的数据验证了这套框架：公众号从手动日产 1 篇到自动化日产 1 篇，质量没降，但我的参与时间从每天 3 小时降到了 30 分钟。

> 不是 Agent 替我写文章，是 Agent 把我从「写」这件事里解放出来了。
